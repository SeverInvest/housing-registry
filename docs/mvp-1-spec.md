# Housing Registry — спецификация MVP-1

## 1. Назначение

`housing-registry` — всероссийский реестр объектов жилищного фонда, способов управления домами и организаций, управляющих домами.

Проект должен последовательно собирать открытые сведения по регионам России, сохранять их в PostgreSQL и предоставлять административный интерфейс Django Admin.

Архитектура не должна быть привязана к Ярославской области. Первичная разработка и проверка выполняются на одном регионе, после чего подключаются остальные регионы.

## 2. Цели MVP-1

MVP-1 должен обеспечивать:

1. ведение справочника регионов;
2. хранение домов и их характеристик;
3. хранение управляющих организаций;
4. хранение текущих и завершённых периодов управления домами;
5. региональный поиск новых домов в ГИС ЖКХ;
6. пагинацию поисковой выдачи по 100 записей;
7. однократное получение подробной карточки нового дома;
8. повторную попытку получения карточки, если предыдущий запрос завершился ошибкой;
9. последующее обновление управляющих организаций из отдельного источника сведений о лицензиях;
10. работу с данными через Django Admin.

## 3. Границы MVP-1

В MVP-1 не входят:

- публичный веб-интерфейс;
- ИИ-агент;
- история изменения всех полей дома;
- `HouseVersion`;
- `ImportRun`;
- отдельная модель `AdministrativeAppointment`;
- хранение исходного JSON поиска;
- хранение исходного JSON подробной карточки;
- `search_hash`;
- `needs_detail_refresh`;
- `first_seen_at`;
- `last_seen_at`;
- `last_changed_at`;
- `is_active` у дома;
- автоматическое повторное получение уже успешно загруженной подробной карточки;
- собственники и участники организаций;
- история руководителей;
- финансовые показатели организаций;
- проверка контрагентов;
- публичное API.

## 4. Общая модель данных

Связи:

- один регион содержит много домов;
- один дом может последовательно управляться разными организациями;
- одна организация может управлять многими домами;
- связь дома и организации хранится в `HouseManagement`;
- при непосредственном управлении поле организации в `HouseManagement` может быть пустым.

Основные модели:

1. `Region`;
2. `House`;
3. `Organization`;
4. `HouseManagement`.

## 5. Region

Справочник регионов России и настроек их синхронизации.

| Поле | Тип | Правила |
|---|---|---|
| `id` | `BigAutoField` | Внутренний первичный ключ |
| `code` | `CharField` | Код региона, строка длиной до 3 символов, уникальный |
| `name` | `CharField` | Наименование региона, уникальное |
| `fias_guid` | `UUIDField` | GUID региона в ФИАС, может быть пустым до настройки |
| `sync_enabled` | `BooleanField` | Разрешён ли импорт региона |
| `created_at` | `DateTimeField` | Дата создания записи |
| `updated_at` | `DateTimeField` | Дата последнего изменения |

`fias_guid` используется при формировании регионального запроса к ГИС ЖКХ.

## 6. House

### 6.1. Идентификаторы

| Поле | Тип | Правила |
|---|---|---|
| `id` | `BigAutoField` | Внутренний первичный ключ |
| `region` | `ForeignKey(Region)` | Внешний ключ, `on_delete=PROTECT` |
| `gis_guid` | `UUIDField` | Основной уникальный идентификатор дома в ГИС ЖКХ |
| `gis_address_guid` | `CharField` | Идентификационный код адреса дома в ГИС ЖКХ |
| `fias_guid` | `UUIDField` | GUID дома в ФИАС, индексируемый, может отсутствовать |
| `house_uid` | `CharField` | Дополнительный идентификатор объекта из ответа ГИС ЖКХ |
| `cadastre_number` | `CharField` | Кадастровый номер, индексируемый, может отсутствовать |

Дом идентифицируется прежде всего по `gis_guid`.

Адрес нельзя использовать как единственный ключ идентификации.

### 6.2. Адрес

| Поле | Назначение |
|---|---|
| `postal_code` | Почтовый индекс |
| `district` | Район |
| `city` | Город |
| `settlement` | Населённый пункт |
| `planning_structure_element` | Элемент планировочной структуры |
| `street` | Улица |
| `building_number` | Номер дома вместе с корпусом, литером и строением |
| `address` | Полный адрес, собранный из компонентов |

`building_number` хранится одной строкой.

Примеры:

- `14`;
- `14 корпус 2`;
- `14 строение 3`;
- `14 литер А`;
- `19/13`.

Нельзя автоматически разделять номер, корпус, литер и строение на отдельные поля.

При формировании `address` используется стабильный порядок:

1. почтовый индекс;
2. регион;
3. район;
4. город или населённый пункт;
5. элемент планировочной структуры;
6. улица;
7. `building_number`.

Пустые компоненты пропускаются. Лишние пробелы удаляются. Исходное написание значимых частей адреса сохраняется.

### 6.3. Характеристики дома

| Поле | Тип | Назначение |
|---|---|---|
| `house_type` | `CharField` | Тип дома |
| `condition` | `CharField` | Состояние |
| `life_cycle_stage` | `CharField` | Стадия жизненного цикла |
| `construction_year` | `PositiveSmallIntegerField` | Год постройки |
| `commissioning_year` | `PositiveSmallIntegerField` | Год ввода в эксплуатацию |
| `reconstruction_year` | `PositiveSmallIntegerField` | Год реконструкции |
| `floors` | `PositiveSmallIntegerField` | Количество этажей |
| `wall_material` | `CharField` | Материал стен |

Все характеристики допускают отсутствие значения, если источник его не предоставляет.

### 6.4. Площади и помещения

Площади хранятся через `DecimalField` с точностью не менее четырёх знаков после запятой.

| Поле | Назначение |
|---|---|
| `area_total` | Общая площадь дома |
| `area_residential` | Поле источника «Жилая площадь в доме» |
| `residential_premises_area` | Общая площадь жилых помещений |
| `non_residential_premises_area` | Общая площадь нежилых помещений |
| `residential_premises_count` | Количество жилых помещений |
| `non_residential_premises_count` | Количество нежилых помещений |

Семантика полей площади должна проверяться по фактическим названиям и значениям в ответах ГИС ЖКХ. Нельзя объединять разные показатели только из-за похожих названий.

### 6.5. Технические поля

| Поле | Назначение |
|---|---|
| `detail_fetched_at` | Дата успешного получения подробной карточки |
| `created_at` | Дата создания записи |
| `updated_at` | Дата последнего изменения записи |

Если `detail_fetched_at` имеет значение, подробная карточка автоматически повторно не запрашивается.

Если `detail_fetched_at` равно `NULL`, следующая синхронизация должна повторить запрос подробной карточки.

## 7. Organization

В MVP-1 хранятся только основные сведения об организации.

| Поле | Тип | Правила |
|---|---|---|
| `id` | `BigAutoField` | Внутренний первичный ключ |
| `gis_guid` | `UUIDField` | GUID организации в ГИС ЖКХ, уникальный при наличии |
| `full_name` | `CharField` | Полное наименование |
| `short_name` | `CharField` | Сокращённое наименование |
| `ogrn` | `CharField` | ОГРН или ОГРНИП, уникальный при наличии |
| `inn` | `CharField` | ИНН, индексируемый |
| `kpp` | `CharField` | КПП |
| `organization_type` | `CharField` | Тип организации |
| `legal_form` | `CharField` | Организационно-правовая форма |
| `legal_address` | `CharField` | Юридический адрес |
| `website` | `URLField` | Сайт |
| `phone` | `CharField` | Телефон |
| `created_at` | `DateTimeField` | Дата создания записи |
| `updated_at` | `DateTimeField` | Дата последнего изменения |

Организацию нельзя сопоставлять только по наименованию.

При импорте используется следующий приоритет сопоставления:

1. ОГРН;
2. GUID организации в ГИС ЖКХ;
3. точная пара ИНН + КПП;
4. создание новой организации.

ИНН без КПП не должен автоматически объединять организации, если источник допускает филиалы или обособленные подразделения.

## 8. HouseManagement

`HouseManagement` является промежуточной моделью связи между домом и управляющей организацией и одновременно хранит историю периодов управления.

| Поле | Тип | Правила |
|---|---|---|
| `id` | `BigAutoField` | Внутренний первичный ключ |
| `house` | `ForeignKey(House)` | Дом |
| `organization` | `ForeignKey(Organization)` | Может быть `NULL` при непосредственном управлении |
| `management_method` | `CharField` + `TextChoices` | Способ управления |
| `management_basis` | `CharField` + `TextChoices` | Основание управления |
| `date_start` | `DateField` | Начало периода управления, если известно |
| `date_finish` | `DateField` | Окончание периода управления, если известно |
| `is_active` | `BooleanField` | Является ли связь действующей |
| `source` | `CharField` + `TextChoices` | Источник сведений |
| `created_at` | `DateTimeField` | Дата создания записи |
| `updated_at` | `DateTimeField` | Дата последнего изменения |

Поля `first_seen_at` и `last_seen_at` не используются.

### 8.1. Способ управления

Внутренние значения:

| Значение | Отображаемое название |
|---|---|
| `management_company` | Управляющая организация |
| `hoa_tsn` | ТСЖ или ТСН |
| `housing_cooperative` | ЖСК или ЖК |
| `direct` | Непосредственное управление |
| `not_selected` | Способ управления не выбран |
| `other` | Иной способ |
| `unknown` | Не определено |

Значение ГИС ЖКХ `УО` преобразуется в `management_company`.

Неизвестное значение источника нельзя без основания относить к одному из известных вариантов. Оно преобразуется в `unknown` и фиксируется в журнале выполнения команды.

### 8.2. Основание управления

| Значение | Отображаемое название |
|---|---|
| `owners_decision` | Выбор собственниками |
| `developer_contract` | Договор с застройщиком |
| `municipal_competition` | Муниципальный конкурс |
| `administrative_appointment` | Назначение администрацией |
| `unknown` | Основание не определено |

Основание управления нельзя определять только по факту наличия организации в лицензии.

Если источник не содержит надёжного основания, сохраняется `unknown`.

### 8.3. Источник сведений

| Значение | Назначение |
|---|---|
| `gis_search` | Региональная поисковая выдача ГИС ЖКХ |
| `gis_detail` | Подробная карточка дома |
| `license_registry` | Реестр лицензий |
| `administrative_registry` | Реестр назначенных администрацией организаций |
| `manual` | Ручное внесение через административный интерфейс |

### 8.4. Ограничения

Для одного дома допускается не более одной активной записи `HouseManagement`.

Если одновременно указаны `date_start` и `date_finish`, дата окончания не может быть раньше даты начала.

`date_start` и `date_finish` обозначают период управления домом. Они не должны автоматически трактоваться как даты выдачи, включения или исключения самой лицензии.

При непосредственном управлении `organization` должна быть пустой.

## 9. Региональный поиск домов

### 9.1. Назначение

Региональный поиск выполняется для обнаружения новых домов, а не для постоянного обновления всех характеристик ранее загруженных домов.

Плановая периодичность после развёртывания — один раз в неделю.

В период разработки команда запускается вручную.

### 9.2. Параметры

- Обрабатываются только регионы с `sync_enabled=True`.
- Используется региональный запрос ГИС ЖКХ, восстановленный по HAR.
- Размер страницы — 100 записей.
- Номер страницы увеличивается последовательно.
- Обход завершается по признаку последней страницы, общему количеству записей либо пустому ответу.

Параметры запросов и URL не должны содержать авторизационные данные в исходном коде.

### 9.3. Обработка результата

Для каждой записи:

1. получить `gis_guid`;
2. если `gis_guid` отсутствует — не создавать дом и вывести диагностическое сообщение;
3. найти дом по `gis_guid`;
4. если дом отсутствует — создать запись с доступными поисковыми данными;
5. если дом существует и `detail_fetched_at` заполнено — пропустить его;
6. если дом новый либо `detail_fetched_at=NULL` — запросить подробную карточку.

Повторный запуск не должен создавать дубликаты домов, организаций или активных связей управления.

Ранее загруженный дом не деактивируется только потому, что временно отсутствует в очередной поисковой выдаче.

## 10. Подробная карточка дома

Переход выполняется по ссылке «Сведения об объекте жилищного фонда».

Подробная карточка автоматически запрашивается один раз — при появлении нового дома.

При успешном ответе:

1. обновляются идентификаторы и адресные компоненты;
2. заполняются характеристики дома;
3. заполняются площади и количество помещений;
4. создаётся или обновляется организация;
5. создаётся первоначальная запись `HouseManagement`;
6. в `detail_fetched_at` записывается текущее время.

Если запрос или сохранение завершились ошибкой:

- `detail_fetched_at` остаётся `NULL`;
- дом не удаляется;
- следующая синхронизация повторяет запрос;
- частично полученные данные не должны оставлять противоречивое состояние.

Сохранение подробной карточки выполняется транзакционно.

После успешного заполнения `detail_fetched_at` автоматические повторные запросы карточки не выполняются.

## 11. Изменение управляющей организации

Подробная карточка дома не используется для регулярного отслеживания смены управляющей организации.

Изменения должны поступать из отдельного источника сведений о лицензиях.

Алгоритм:

1. найти дом по устойчивому идентификатору;
2. определить текущий способ управления и организацию;
3. найти активную запись `HouseManagement`;
4. если сведения не изменились — ничего не создавать;
5. если управление изменилось:
   - закрыть предыдущую запись;
   - установить `is_active=False`;
   - заполнить `date_finish`, если источник сообщает надёжную дату;
   - создать новую активную запись;
6. основание управления заполнять только при наличии надёжных данных.

Если дом перешёл на непосредственное управление, создаётся активная запись с соответствующим способом управления и пустой организацией.

Точный контракт источника лицензий должен быть зафиксирован на основании отдельного HAR или официального набора открытых данных до реализации этого импортера.

## 12. HTTP-клиент

HTTP-клиент должен поддерживать:

- тайм-ауты;
- ограниченное количество повторных попыток;
- повторные попытки при временных сетевых ошибках и ответах `429`/`5xx`;
- отсутствие повторных попыток для обычных ошибок `4xx`;
- понятный `User-Agent`;
- последовательную и бережную загрузку;
- диагностические сообщения без Cookie, токенов и персональных данных.

Нельзя обходить ограничения доступа сайта или механизмы авторизации.

## 13. Журналирование MVP-1

Отдельная модель `ImportRun` в MVP-1 не создаётся.

Management command выводит в консоль итоговую статистику:

- обработано страниц;
- найдено записей;
- создано домов;
- пропущено существующих домов;
- успешно загружено карточек;
- карточек с ошибкой;
- создано организаций;
- создано или изменено связей управления;
- количество ошибок.

Секреты и полные HTTP-заголовки в журнал не выводятся.

## 15. Тестирование

Обязательные сценарии:

1. сборка полного адреса из компонентов;
2. сохранение `building_number` без разделения;
3. преобразование известных способов управления;
4. обработка неизвестного способа управления;
5. создание нового дома;
6. повторный импорт без дубликата;
7. пагинация по 100 записей;
8. однократное получение успешной подробной карточки;
9. повтор карточки при `detail_fetched_at=NULL`;
10. отсутствие повторного запроса при заполненном `detail_fetched_at`;
11. сопоставление организации по ОГРН;
12. запрет сопоставления только по наименованию;
13. непосредственное управление без организации;
14. закрытие предыдущего периода при смене управления;
15. запрет двух активных `HouseManagement` для одного дома;
16. транзакционный откат при ошибке сохранения карточки.

Тесты не должны выполнять реальные запросы к ГИС ЖКХ.

Фикстуры должны быть очищены от авторизационных заголовков, Cookie, токенов и персональных данных.

## 16. Последовательность реализации

1. привести модели к утверждённой структуре;
2. создать и проверить миграции;
3. настроить Django Admin;
4. реализовать mapper поискового ответа;
5. реализовать региональную пагинацию;
6. проверить импорт одной страницы;
7. проверить импорт одного региона;
8. реализовать получение подробной карточки;
9. реализовать повтор карточек с `detail_fetched_at=NULL`;
10. зафиксировать контракт источника лицензий;
11. реализовать обновление `HouseManagement`;
12. развернуть PostgreSQL и приложение на Yandex Cloud;
13. настроить еженедельный запуск.
