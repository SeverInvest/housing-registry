# Правила работы с проектом housing-registry

## Назначение проекта

`housing-registry` — публичный всероссийский реестр объектов жилищного фонда, способов управления домами и управляющих организаций.

Основной источник данных MVP-1 — открытые данные ГИС ЖКХ.

Технологический стек:

- Python 3.12+;
- Django;
- PostgreSQL;
- Django Admin;
- Docker Compose для локальной инфраструктуры.

## Источники требований

Перед изменением моделей, импорта или административного интерфейса необходимо прочитать:

1. `docs/mvp-1-spec.md` — утверждённая структура данных и границы MVP-1;
2. `README.md` — установка и запуск проекта;
3. существующий код и тесты.

Если код противоречит спецификации, нельзя молча выбирать один из вариантов. Нужно описать противоречие и запросить решение.

## Язык

- Общение с владельцем проекта и документация — на русском языке.
- Имена классов, функций, переменных и полей БД — на английском языке.
- Названия полей должны быть понятными без внутренних сокращений, кроме общепринятых: `gis`, `fias`, `ogrn`, `inn`, `kpp`.

## Рабочее окружение

Локальное виртуальное окружение расположено в `.venv`.

Команды необходимо запускать через его Python:

```bash
./.venv/bin/python manage.py check
./.venv/bin/python -m ruff check .
./.venv/bin/python -m pytest
```

Для установки зависимостей:

```bash
./.venv/bin/python -m pip install -r requirements-dev.txt
```

Не следует рассчитывать на то, что виртуальное окружение активировано в оболочке.

## Порядок работы

Перед внесением изменений:

1. проверить `git status`;
2. изучить связанные файлы и спецификацию;
3. для сложной задачи сначала предложить план;
4. указать спорные решения и задать необходимые вопросы;
5. не расширять задачу без согласования.

После внесения изменений:

1. показать перечень изменённых файлов;
2. кратко описать изменения;
3. выполнить необходимые проверки;
4. проверить итоговый diff;
5. сообщить о непроверенных предположениях и ограничениях.

Не создавать коммиты и не выполнять `git push`, если это прямо не поручено пользователем.

## Git

- Один коммит должен содержать одно логически завершённое изменение.
- Не использовать `git push --force`.
- Не переписывать историю репозитория без прямого указания.
- Не удалять пользовательские изменения.
- Перед коммитом выполнять `git diff --cached --check`.
- Перед добавлением файлов проверять отсутствие секретов и временных данных.

## Безопасность

Репозиторий публичный.

Запрещено добавлять в Git:

- `.env`;
- пароли;
- API-ключи;
- Django `SECRET_KEY`;
- Cookie;
- заголовки `Authorization`;
- session ID;
- токены из HAR;
- приватные ключи и сертификаты;
- реальные параметры доступа к PostgreSQL;
- исходные HAR-файлы, если они содержат авторизационные данные.

В `.env.example` разрешены только безопасные значения-заглушки.

Нельзя выводить секреты в консоль, ответы агента, тестовые отчёты и журналы.

## Правила Django

- Внутренний первичный ключ моделей называется `id`.
- Поле внешнего ключа в модели называется по сущности: `region`, `house`, `organization`.
- Django самостоятельно создаёт столбцы `region_id`, `house_id`, `organization_id`.
- Не создавать поля `id_region`, `id_house` и `id_organization`.
- Денежные показатели и площади хранить через `DecimalField`, а не `FloatField`.
- Для справочных значений использовать `TextChoices`.
- Все даты и время должны быть timezone-aware.
- Использовать `USE_TZ = True`.
- Новые изменения моделей должны сопровождаться миграциями.
- Уже опубликованные миграции нельзя переписывать без отдельного решения.
- Бизнес-логику импорта нельзя размещать в моделях или `admin.py`.

## Архитектура импорта

Сетевые запросы, преобразование данных и сохранение должны быть разделены.

Рекомендуемое разделение:

- API-клиент — HTTP-запросы;
- mapper — преобразование ответа ГИС ЖКХ во внутреннюю структуру;
- service/upsert — транзакционное сохранение;
- management command — запуск и вывод результатов.

Импорт должен быть:

- идемпотентным;
- повторяемым;
- устойчивым к частично отсутствующим данным;
- безопасным при повторном запуске;
- покрытым тестами без реальных сетевых запросов.

Нельзя идентифицировать дом только по текстовому адресу.

Нельзя идентифицировать организацию только по наименованию.

## Ограничения MVP-1

Без отдельного согласования не добавлять:

- `HouseVersion`;
- `ImportRun`;
- `AdministrativeAppointment`;
- исходные JSON-ответы в модели;
- контрольные хеши поисковых данных;
- историю изменения реквизитов организаций;
- собственников и руководителей организаций;
- финансовую отчётность;
- публичный пользовательский интерфейс;
- ИИ-агента.

Полная спецификация MVP-1 находится в `docs/mvp-1-spec.md`.

## Проверки

После изменения Python-кода необходимо выполнить:

```bash
./.venv/bin/python manage.py check
./.venv/bin/python -m ruff check .
./.venv/bin/python -m pytest
```

После изменения моделей дополнительно выполнить:

```bash
./.venv/bin/python manage.py makemigrations --check --dry-run
```

Если проверка не запустилась, это нельзя считать успешным результатом. Нужно показать причину.

Тесты импорта не должны обращаться к реальной ГИС ЖКХ. Ответы внешнего сервиса необходимо подменять очищенными фикстурами.

## Критерии завершения задачи

Задача считается завершённой, когда:

- реализованы только согласованные изменения;
- проверки выполнены успешно;
- секреты не попали в Git;
- обновлена связанная документация;
- итоговый diff проверен;
- результат и ограничения понятно описаны пользователю.
